FleetGraph · Agent-native project intelligence for Ship

Graph-backed proactive path, shared agent architecture

FleetGraph is not just a detector plus a chat panel. It is a Ship-native agent loop: Ship domain context feeds an outcome engine, the outcome engine creates findings and action candidates, and the compiled FleetGraph runtime now branches between proactive at-risk Week detection and on-demand chat inside the same graph entry point.

Domain layer Programs, projects, Week documents, issues, standups, plans, retros, people, and ownership are first-class context.
Outcome layer Findings, action candidates, approvals, and suppressions are persisted agent outcomes; chat answers remain scoped client-side outputs.
Execution layer LangGraph powers proactive detection and on-demand chat; the chat route still owns HTTP auth, validation, rate limits, and SSE framing.

MVP boundary

The MVP implements one at-risk Week detector graph end to end. Stale blocker, missing progress, planless Week, and overload signals are implemented as risk patterns inside that graph and validated by detection-quality traces; separate detector modules remain future hardening. On-demand chat now enters the shared FleetGraph runtime for traced SSE streaming, while chat-initiated write actions remain a post-MVP extension. This page is a supplemental explainer; FLEETGRAPH.md remains the canonical submission artifact.

Proactive — the agent pushes

Triggered by the in-process poll tick or a debounced Ship mutation. The server-side agent uses scoped service access; it does not impersonate a browser session.

trigger + lock

The tick can run on every API instance in a multi-instance deployment, so each project run first takes a non-blocking Postgres advisory lock. Existing findings for the same scoped document and material-change key, including pending_review findings, quiet duplicate runs.

scope

Workspace membership authorizes access. Recipient resolution is separate: Week owners, project owners, issue assignees, person documents, and explicit accountability fields decide who is responsible and who should be notified.

context

The agent reasons over Ship-native context: program, project hypothesis, Week document (document_type: "sprint"), issues, standups, plans, retros, people, and prior findings.

quiet gates

Quieting is not just a content hash. Change-detect reads durable finding state, elapsed-time signals, dismissals, snoozes, and rejection feedback before spending model tokens or notifying.

reason + candidate

The model produces a structured finding plus an ActionCandidate: owner, role reason, urgency, evidence, target Ship object, recommended action, and approval level.

approval

Consequential actions persist as pending_review with action metadata. The inbox lets authorized recipients approve, edit, reject, dismiss, or snooze; resume requires the recipient or a workspace admin.

output

The database-backed inbox is the source of truth. /events only invalidates/refetches the UI for live awareness, so missed pushes are reconciled on load, focus, reconnect, or poll.

On-demand — the user pulls

Triggered from embedded chat inside the current Ship document. The HTTP route remains /api/fleetgraph/chat for auth, validation, rate limiting, and SSE framing; the model stream runs inside the on-demand branch of the shared FleetGraph runtime.

context parity

The agent gets what the user sees: doc type, doc id, project, Week document, nearby issues, recent standups, open findings, and pending actions. A chat on a Week knows that Week without the user restating it.

answer path

Questions skip proactive quiet gates and enter the on-demand chat branch of the shared FleetGraph runtime. The chat thread is stable per (userId, docId), trims to a sliding message window, refetches Ship state every turn, and streams tokens over SSE from inside the graph.

action path

Action requests are not out of scope for FleetGraph. The current MVP defers browser-visible chat action creation; the target architecture routes those requests into draft actions or pending approvals instead of making chat answer-only forever.

Ship writes

The agent currently reads context, drafts approved comments, dismisses or snoozes findings, and resumes approved draft_comment actions. Create-issue, state-change, and assignment tools are target extensions, not current MVP write primitives.

approval

In the target action extension, explicit user requests can use quick confirmation for low-risk changes. High-stakes or hard-to-reverse actions should enter the same pending approval workflow used by proactive findings.

deployment

Token streaming needs a non-buffered route. /api/fleetgraph/chat should have a non-buffered proxy behavior with compression disabled, or the client should route directly to the API process.

Why this is agent-native

FleetGraph receives events, reasons with dynamic Ship context, persists visible outcomes, and calls the approved Ship write primitive available in the MVP. New behavior should come from new detector prompts and tool composition, not a new bespoke workflow for every use case.

Ship Domain Layer

The graph is grounded in Ship's accountability model, not generic sprint-health data. Authorization, ownership, accountability, and notification targeting are separate concerns.

Programs

Long-lived product or initiative areas. They carry continuity and investment context.

Projects

Hypothesis-driven experiments with outcomes, ownership, and eventual validation.

Week documents

Stored as document_type: "sprint". Dates are computed from the workspace cadence.

People

Person documents and user ids map ownership, assignees, recipients, and accountability.

Outcome Layer

FleetGraph's durable output is not just prose. It is a lifecycle of findings and action candidates that the UI can reconcile, resume, and suppress.

ActionCandidate

  • Target Ship document
  • Owner and role reason
  • Urgency and evidence
  • Recommended action
  • Approval level and reversibility

Finding state

  • open / pending_review
  • approved / executed
  • rejected / dismissed
  • snoozed / expired

Approval matrix

Auto-answer for read-only work; quick confirm for explicit low-risk changes; explicit approval for unsolicited, high-stakes, external, bulk, or hard-to-reverse actions.

Agent Tool Parity

This is the target tool model. Current MVP write execution is limited to approved draft_comment actions plus finding lifecycle operations such as dismiss and snooze. Over time, every action a user can take through Ship should have an equivalent agent capability.

Read primitives

read_current_context, list_project_issues, list_week_standups, read_accountability_status

Draft primitives

create_draft_action, draft_comment, create_draft_issue, rank_action_candidates

Write primitives

post_comment, create_issue, update_issue_state, assign_issue, snooze_finding

Production Guardrails

These constraints are part of the architecture because they decide whether the graph works safely in deployed Ship, not just in a local demo.

Trust boundary

Issue text, standups, plans, and retros are untrusted LLM input. Prompts delimit source content, structured output is size-capped, rendered finding text is encoded, and HITL approval is the backstop for consequential actions.

Workspace isolation

Every finding and action row carries workspace_id. Queries bind workspace, cross-workspace ids are denied, and resume requires a resolved recipient or workspace admin.

Multi-instance safety

Proactive runs take a per-project advisory lock before graph invocation. Dedup protects rows; the lock protects model spend and action execution.

Streaming deployment

Chat SSE requires a non-buffered proxy behavior for /api/fleetgraph/chat or a direct API route. /events remains the live invalidation path for findings.
